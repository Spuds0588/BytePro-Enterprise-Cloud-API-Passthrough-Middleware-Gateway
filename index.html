Loan documents and conditions come first

The two workflows that block real partner integrations are exchanging loan file documents and answering underwriting conditions. Both are implemented, tested locally, and prioritised above every other phase.

Loan document upload & download

POST /v1/loans/{id}/documents queues a base64 PDF up to 180,000 bytes through SQS FIFO and returns 202 with a job ID; larger PDFs up to 5 MB upload synchronously and return 200. GET /v1/loans/{id}/documents lists metadata; GET /v1/loans/{id}/documents/{docId} returns the PDF bytes. A title commitment is the canonical example.

Condition responses

POST /v1/loans/{id}/conditions accepts description and status rows from title and broker keys. Updates are applied by the worker with lock retries, and brokers can read the current conditions on the loan payload.

No document at rest

Small PDFs travel in the queue message; larger PDFs upload directly. Nothing is written to DynamoDB or S3, and files above 5 MB are refused rather than truncated.

Personas are chosen server-side from the invite: TITLE_VENDOR, TPO_BROKER, and read-only AMC_VENDOR. SSN, taxpayer ID, credit score, date of birth, income, assets, and liabilities are stripped at any depth before a response leaves the gateway.

Deploy into your own AWS account

The whole stack is one CloudFormation file with the Lambda bundle inlined, under the 51,200-byte direct-upload limit. It provisions API Gateway, a usage plan, DynamoDB, SQS FIFO with a dead-letter queue, Secrets Manager, and a NAT gateway with a static Elastic IP for BytePro's firewall allowlist.

bash <(curl -sSL https://raw.githubusercontent.com/Spuds0588/BytePro-Enterprise-Cloud-API-Passthrough-Middleware-Gateway/main/deploy.sh)

The installer asks for your BytePro URL, account code, and three service-account credentials, generates role invite codes, deploys the stack, and prints the gateway URL, portal URL, egress IP, and one invite link per role.

What is verified, and what is not

This is shared infrastructure, not a vendor product. The maintainer has no BytePro access and no AWS account for this project, so live verification is a shared responsibility: every deployment that reports back improves it for everyone.

Verified locally

Session login, caching, and 401 refresh; invite provisioning; persona masking; read projection and error mapping; FIFO fee and condition writes with retries; PDF upload, list, and download; validation failures; job ownership; the HTTP runtime; and the exact inline bundle in the template.

Not verified

Any live BytePro call, any live AWS deployment, the real document and condition response shapes, and the NAT allowlist. Upstream routes follow the documented REST convention and are exercised only against the local fake.

Known limits

5 MB uploads (no FIFO retry above 180,000 bytes), no per-loan organization scoping, global per-role invite codes, no webhooks, no loan read cache, no full 1003 write, and no CORS. Each is recorded in todo.md.

FAQ

Does the gateway store loan data or documents?

No. It stores only tenant mappings, per-role session tokens, and job status. Small document bytes travel inside an SQS message; larger PDFs upload directly. Nothing is retained.

Can a title company upload a title commitment?

Yes. Title and broker keys can upload a base64 PDF, list loan documents, and download one by ID. The appraisal persona is read-only.

Why does PATCH /v1/loans/{id} return 501?

A full 1003 loan-field write needs a real BytePro payload shape. Until a sanitized sample arrives, the gateway refuses rather than inventing a contract that looks tested.

Has this been verified against a live BytePro tenant?

No. The maintainer has no BytePro access and no AWS account for this project. Behavior is verified locally against a fake BytePro API; deployment evidence must come from the community.

Does the gateway keep the BytePro service-account passwords?

Only in AWS Secrets Manager, one secret per role. They are never in Lambda environment variables, responses, or logs.

How do I contribute?

Open an issue with sanitized evidence, or a pull request with a regression test. The maintainer is happy to add contributors.

Community maintained — contribute aggressively

This is an independent template, not a BytePro product. Issues and pull requests are the roadmap. Found a defect? Open an issue with a minimal reproduction and the commit you tested. Fixed something? Send a pull request with a regression test and updated docs.

Validated a real BytePro payload or a deployment? Report the sanitized result on the relevant issue — that evidence is the most valuable contribution available. Want to help long term? Say so on your issue or PR.

Never include API keys, invite codes, passwords, session tokens, loan data, or borrower PII in an issue, PR, screenshot, or log. Private forks are discouraged: upstream the smallest fix so every deployment benefits.
